Webhook URL Exposed in Client-Side Code
speedtest-webpage.html — CONFIG.webhookURL
High ▼

Problem

The Power Automate webhook URL is hardcoded inside speedtest-webpage.html inside the CONFIG object. Anyone who opens the browser's View Source or DevTools can read it instantly. The URL is currently empty — but this will become a live risk the moment it is configured.

⚠️ The webhook is currently disabled (webhookURL: ''). This risk activates as soon as a real URL is pasted in.

Risk

  • Anyone can extract the URL and POST fake results — spoofed names, emails, speeds.
  • Automated scripts can flood your Power Automate flow and exhaust execution quotas.
  • The URL structure reveals internal workflow IDs and environment details.

Recommended Fixes

  • Create a lightweight server-side proxy (Azure Function, Node.js) that holds the webhook URL and only forwards requests that include a valid shared token.
  • Add a X-Transpro-Token header to every submission and validate it on the proxy before forwarding.
  • Rotate the webhook URL periodically; restrict inbound IPs on the Power Automate side if supported.

No Authentication — Open to Anyone
speedtest-webpage.html — form has no identity verification
High ▼

Problem

The form accepts any name and email with no verification. There is no login, SSO check, or token gate. Anyone who has the file — or a copy of it — can submit results as any employee.

Risk

  • Fake or malicious submissions pollute your diagnostic data with fabricated results.
  • No way to guarantee the person running the test is the person named in the form.
  • If the HTML file is shared publicly or emailed widely, external parties can submit results.

Recommended Fixes

  • Integrate with Azure Active Directory / Entra ID so only authenticated Transpro accounts can access and submit the form.
  • As a lighter alternative, IT generates single-use tokens (e.g., a GUID) and emails one to each employee before they run the test — the form requires the token to submit.
  • At minimum, the Power Automate flow should cross-reference the submitted email against your employee directory before storing the result.

XSS via innerHTML with External Data
speedtest-webpage.html — displayResults(), row() helper
High ▼

Problem

The displayResults() function builds the results panel by assigning template literals directly to results.innerHTML. Values from two external sources — ipapi.co (ISP name, city, country) and hw-data.js (CPU, OS, machine model) — are embedded without HTML-escaping.

// Vulnerable pattern — data.isp comes from ipapi.co results.innerHTML = `<span>${data.isp}</span>`;

Risk

  • If ipapi.co is compromised or a man-in-the-middle intercepts the response, a malicious ISP value like <img src=x onerror="stealData()"> executes in the user's browser.
  • If hw-data.js is tampered with (e.g., on a shared drive), injected HTML in the CPU or model field runs directly when results are displayed.
  • Chained with the missing CSP (risk #10), an injected script has full page access.

Recommended Fixes

  • Replace innerHTML assignments with DOM methods that treat values as plain text — use textContent for all external values.
  • Or run all external values through an escape function before inserting:
function escHtml(str) { return String(str) .replace(/&/g,'&amp;').replace(/</g,'&lt;') .replace(/>/g,'&gt;').replace(/"/g,'&quot;'); }
  • Validate ipapi.co responses against an expected schema before using any field.

Medium Severity
🗂️
hw-data.js Persists Sensitive System Info on Disk
run-speedtest.ps1 writes hw-data.js alongside the HTML
Medium ▼

Problem

Every time run-speedtest.bat is executed, the PowerShell script overwrites hw-data.js in the project folder with the current machine's CPU model, exact RAM, OS build number, machine model, and network adapter details. This file remains on disk indefinitely after the test.

// hw-data.js after a run — sits on disk until next run overwrites it window._hwData = { cpu: "Intel(R) Core(TM) i5-10400T CPU @ 2.00GHz (6C / 12T)", ram: "32 GB", os: "Microsoft Windows 11 Business (Build 26200)", model: "LENOVO 11DUS94400", netType: "Ethernet", netSpeed: "1 Gbps", ... };

Risk

  • If the project folder is on a shared drive, any user with read access can see the last machine's hardware profile.
  • If hw-data.js is accidentally committed to version control or emailed, machine fingerprint data leaks.
  • An attacker with write access to the folder can inject malicious JS into hw-data.js, which the HTML will execute as a script tag (see XSS risk above).

Recommended Fixes

  • Add hw-data.js to .gitignore immediately to prevent accidental commits.
  • Have the PS script delete hw-data.js after the browser finishes loading (e.g., after a short delay, or use a file watcher).
  • Restrict folder permissions so only the running user can write to the project directory.
  • Validate window._hwData fields against an expected schema/character allowlist before using them in the HTML.

No Rate Limiting — Spam / Flood Risk
speedtest-webpage.html — runSpeedTest() has no submission cooldown
Medium ▼

Problem

There is no limit on how many times the form can be submitted. The "Run Another Test" button re-enables immediately after each test. Client-side button disabling is trivially bypassed via browser DevTools or scripting.

Risk

  • An automated script can submit hundreds of fake results per minute to Power Automate.
  • Power Automate has monthly execution limits — a flood can exhaust your plan quota and drop real submissions.
  • Garbage data degrades the reliability of IT diagnostics.

Recommended Fixes

  • Add a client-side cooldown: after a successful submission, disable the button for 5 minutes and show a countdown.
  • Implement server-side rate limiting on the proxy (if one is added for risk #1) — e.g., max 3 submissions per IP per hour.
  • Add Cloudflare Turnstile or Google reCAPTCHA v3 to block automated submissions without requiring user interaction.

No Input Validation or Sanitization
speedtest-webpage.html — form fields sent raw to webhook
Medium ▼

Problem

Name, email, department, and location are sent verbatim to the webhook with no server-side validation. The browser's required and type="email" attributes are the only checks — both are trivially bypassed by editing the DOM or sending a raw HTTP request.

Risk

  • Malicious content in fields (script tags, SQL fragments, formula injection) propagates into Power Automate and wherever it writes data — SharePoint, Excel, Dataverse.
  • If results are exported to CSV and opened in Excel, a name field like =CMD|'/c calc'!A0 triggers formula injection.
  • Oversized inputs can cause unexpected behavior in downstream systems.

Recommended Fixes

  • Validate and sanitize all inputs server-side — never trust client-side checks alone.
  • Enforce character allowlists for name and location (letters, spaces, hyphens, apostrophes only) and enforce a max length.
  • Strip or encode any HTML and formula-trigger characters (<, >, =, +, @) before writing to any data store.

Third-Party Dependency on ipapi.co
speedtest-webpage.html — getUserIP() fetches https://ipapi.co/json/
Medium ▼

Problem

Every time the test runs, the user's real public IP address is sent to ipapi.co, a third-party commercial service, to retrieve ISP, city, region, and country. You have no control over what ipapi.co does with this data.

Risk

  • Employee IP addresses and inferred locations are shared with an external service with no data processing agreement in place.
  • If ipapi.co is down or rate-limits your requests (free tier limit applies), the entire test fails to collect IP/ISP data silently.
  • A compromised or malicious response from ipapi.co feeds directly into the XSS vulnerability (risk #3).

Recommended Fixes

  • Route IP lookups through your own backend (Azure Function) using a self-hosted database like MaxMind GeoLite2 — no employee IP data leaves your infrastructure.
  • If a third-party service is acceptable, at minimum validate and sanitize every field in the response before using it.
  • Sign a Data Processing Agreement (DPA) with ipapi.co if employee data is involved and PIPEDA/GDPR compliance is required.

PowerShell ExecutionPolicy Bypass
run-speedtest.bat — launches PS1 with -ExecutionPolicy Bypass
Low ▼

Problem

run-speedtest.bat invokes PowerShell with -ExecutionPolicy Bypass to run run-speedtest.ps1, which is unsigned. This bypasses the PowerShell execution policy that organizations use as a defense against unauthorized script execution.

powershell.exe -ExecutionPolicy Bypass -NoProfile -File "%~dp0run-speedtest.ps1"

Risk

  • If an attacker replaces run-speedtest.ps1 with a malicious script (e.g., on a shared drive), the bat will run it with bypass — no execution policy check will stop it.
  • In environments with enforced AllSigned or RemoteSigned policy, this directly violates the corporate security baseline.
  • Teaches employees to bypass security prompts, which is poor security hygiene.

Recommended Fixes

  • Code-sign run-speedtest.ps1 with your organization's code signing certificate — then remove the -ExecutionPolicy Bypass flag.
  • Restrict write access to the project folder so only IT admins can modify the PS1 file.
  • As an alternative, set the execution policy on managed machines to RemoteSigned and sign the script accordingly.

No Privacy Notice or Data Consent
speedtest-webpage.html — form collects PII with no disclosure
Legal ▼

Problem

The form collects name, email, public IP, ISP, browser fingerprint, OS version, CPU model, and RAM — but displays no privacy notice explaining what is collected, why, how long it is stored, or who has access.

Risk

  • Under PIPEDA (Canada), organizations must inform individuals about the personal information collected and obtain meaningful consent before collecting it.
  • If any employees are EU-based, GDPR requires explicit, informed consent prior to collecting personal data including IP addresses and device identifiers.
  • Non-compliance can result in regulatory investigation, fines, and reputational damage.

Recommended Fixes

  • Add a short disclosure above the form: "This test collects your name, email, IP address, ISP, and device information. Results are stored by Transpro IT and used solely for network diagnostics."
  • Add a required checkbox: "I understand and consent to the collection of this data."
  • Consult your legal/compliance team to confirm jurisdiction-specific requirements.

No HTTPS Enforcement
speedtest-webpage.html — no transport security check
Low ▼

Problem

The tool currently runs as a local file:// page, which avoids HTTP-level interception. However, if the file is ever moved to an HTTP web server (intranet, SharePoint, etc.) without TLS, all data transmits in cleartext.

Risk

  • An attacker on the same network can intercept form submissions and read employee names, emails, IPs, and hardware details in plaintext.
  • The webhook POST containing all collected data would also be visible in plaintext.
  • Modern browsers block mixed-content requests — an HTTP page cannot POST to an HTTPS webhook, breaking functionality.

Recommended Fixes

  • Host the page on an HTTPS endpoint only — Azure Static Web Apps, SharePoint, or any TLS-enabled server.
  • Add an HTTP-to-HTTPS redirect check at page load:
if (location.protocol === 'http:') location.replace('https:' + location.href.substring(5));

No Content Security Policy (CSP)
speedtest-webpage.html — no script/connect restrictions
Low ▼

Problem

There are no CSP headers or meta tags restricting which scripts, connections, or resources the page can load. Without CSP, the XSS vulnerability (risk #3) has maximum blast radius — an injected script can load external resources, exfiltrate data, and contact any domain.

Recommended Fixes

  • Add a <meta> CSP tag in <head> whitelisting only the origins the page requires:
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self' 'unsafe-inline'; connect-src https://ipapi.co https://speed.cloudflare.com https://YOUR-WEBHOOK-DOMAIN; style-src 'self' 'unsafe-inline';">
  • Remove 'unsafe-inline' for scripts by moving all JS to an external file and using a nonce or hash instead.
  • Prefer setting CSP as an HTTP response header (stronger than meta tag) if hosting on a web server.
